# Architecture

A technical map of how this profile is built, for anyone who wants to read beneath the surface.

## Design principle

Every element here either *does something real* or *shows real understanding*. Decorative
elements are acceptable only if they carry genuine technical substance underneath — a 3D scene
running a custom GLSL shader, not a screenshot; a compiler playground that actually compiles,
not a syntax-highlighted screenshot of code.

## 3D engine distribution

Each scene deliberately uses a different rendering technology to demonstrate breadth — this
isn't arbitrary, it mirrors the kind of multi-layer thinking the work actually requires:

| Scene | Engine | Why this engine |
|-------|--------|-----------------|
| Quantum Atom | Babylon.js + WebXR | PBR materials, GlowLayer, VR-capable |
| DNA Helix | Babylon.js | PBR iridescence (thin-film interference) |
| Particle Field | WebGPU + WGSL compute | 1M particles on GPU, no CPU bottleneck |
| Skill Universe | OGL (50KB) | Minimal — shows understanding, not reliance on abstraction |
| Neural Network | Raw WebGL2 | Instanced drawing, GLSL ES 3.0, zero dependencies |
| Void Portal | Raw WebGL2 | Pure fragment shader, 4-octave fbm noise |
| Hologram Cube | Three.js + CSS3D | Hybrid 3D+DOM rendering |
| CPU Die | Three.js | Shared ShaderMaterial, smootherStep easing |
| void-engine | Rust → wgpu → WASM | Compiled, not interpreted — same wgpu targets native Vulkan/Metal/DX12 |

**Actually run, not just read.** This diagram and the seven workflow YAML
files were checked past syntax validity this pass: `npm install`, then the
real vitest suite (29/29 passing, including the tests that check
`resume.json` doesn't fabricate a CV and that the integrity manifest is
well-formed), the real visual-regression script (produced 31 fresh
baselines exactly as its own code comment says a first run should, no
false failures), and `node scripts/generate-research.js` against the
actual `data/research-log.yaml` and `README.md` in this repo.

That last one caught a real bug, not a hypothetical one: the script
decided whether the `RESEARCH_LOG_START`/`END` markers existed in
`README.md` by checking whether `readme.replace(...)` changed the string —
but when the README is already in sync with the YAML (the normal,
steady-state case), the regex matches and replaces with byte-identical
output, so that check wrongly concluded the markers were missing and set
a nonzero exit code. `update-readme.yml`'s `inject-easter-eggs` job runs
this script with no `continue-on-error`, so every daily cron run would
have failed that job right at this step — before it ever reached the
commit step that pushes the refreshed SVG easter eggs, integrity
manifest, and research log — whenever the README was already correct.
Fixed by testing the marker regex directly (`MARKER_RE.test(readme)`)
instead of inferring its presence from whether the output changed;
re-ran the script against both the in-sync case (exit 0, renders
correctly) and a deliberately-marker-stripped copy (exit 1, correct
warning) to confirm the fix distinguishes them.

`lighthouserc.json`'s URL list also only covered `index.html` plus the
four functional tools and `system-map` — the nine 3D scenes get
assembled into `dist/` by both `deploy-pages.yml` and
`lighthouse-ci.yml` but were never in the list Lighthouse actually
audits, so the `color-contrast: error` / `target-size: error` assertions
never touched the pages where most of this pass's WCAG work happened.
Added all nine (plus `rust-engine`) to the URL list; Lighthouse's
accessibility checks run against rendered DOM/CSSOM regardless of
whether a scene's WebGPU/WebGL canvas actually paints in a headless
runner, so this holds even for scenes that fall back to their
no-context UI in CI.

**Whole-repo sweep, not just the pass above.** README.md, every SVG
under `assets/svg/`, and every `.md`/`.html`/`.js`/`.json`/`.yaml`/`.yml`/
`.svg`/`.rs`/`.wgsl`/`.toml` file in the repo were checked programmatically
for the two hard content rules from the project brief — zero emoji, zero
Arabic outside this conversation — with none found. All 31 SVGs parse as
well-formed XML; none reference Google Fonts or use the invalid `&nbsp;`
entity. Every local asset path README.md references (41 total) exists on
disk, and every internal `noor-alhussain.github.io` link in README maps
to an actual `dist/` output path in `deploy-pages.yml` — the short URLs
(`/atom/`, `/cpu/`, etc.) are an intentional rename during deploy, not
broken links, confirmed by cross-referencing both files rather than
assuming the shorter slugs were a mistake.

`update-readme-badges.js` had the same class of gap as the
`generate-research.js` bug above, one level milder: it had no marker-
presence check at all, so if `LAST_BUILD_BADGE`/`LOC_BADGE` markers ever
went missing from README.md, `readme.replace()` would silently no-op and
the script would still log a false "Badges updated" success. Added the
same `MARKER_RE.test()` guard; verified both paths by running it against
a throwaway copy — succeeds normally when markers are present, exits 1
with a clear error when they're stripped, no more silent false success.

Also confirmed: this environment has real network access this session
(`npm install` succeeded repeatedly) but genuinely has no Rust toolchain
installed (`rustc`/`cargo` both report "not found") — the earlier
Verification Status table's Rust row previously blamed both network and
toolchain; corrected to name the toolchain as the actual, sole blocker.

**A real bug in the Rust source, found without a compiler.** With no
`rustc` available, `lib.rs`, `math.rs`, and `shader.wgsl` were checked the
only way this environment can: read end to end, then every crate root
referenced via `::` was extracted and cross-referenced against
`Cargo.toml`'s declared dependencies (the same technique used earlier to
catch the unused `d3`/`cannon-es` npm packages, run in the opposite
direction). `js_sys::Date::now()` is called twice in `lib.rs` for the
render-loop clock, but `js-sys` was never declared as a dependency —
every other crate root resolved cleanly (`std` submodules, `winit`/
`wasm_bindgen`/`wgpu` submodules, or the local `math` module). This would
fail to compile with an unresolved-crate error the first time
`check-rust.yml` actually runs on a real push. Added
`js-sys = "0.3"` to `Cargo.toml`. Separately, the `Uniforms` and vertex
layouts were compared between the Rust structs and the WGSL structs
they're bound to — the vertex side checked out (`array_stride:
size_of::<math::Vertex>()` = 36 bytes, explicit offsets 0/12/24 for
position/normal/color, matching `VertexFormat::Float32x3` three times in
`lib.rs`'s `VertexBufferLayout`, which is what actually governs vertex
byte layout — WGSL's `VertexInput` struct only names the fields, it
doesn't derive their offsets). **The `Uniforms` comparison, on the other
hand, was wrong, and was corrected in the pass documented in "Final
verification round" below: it added up raw field sizes
(`mat4x4<f32>` 64 + `f32` 4 + `vec3<f32>` 12 = 80) without applying
WGSL's mandatory alignment rules for the uniform address space, under
which `vec3<f32>` is 16-byte aligned — not 4 — which pushes the real
total to 96 bytes and would have failed bind-group validation against
the 80-byte buffer `bytemuck::cast_slice` actually produced from the
Rust-side `[f32; 3]`. See that section for the full reasoning and the
fix applied to `_pad`'s size.**

Also found: `Cargo.toml` itself was never in
`generate-integrity-manifest.js`'s glob list — only `src/*.rs` and
`src/*.wgsl` were covered, meaning the Rust project's own dependency
manifest had no integrity coverage at all, unlike `package.json` (which
does). Added it; manifest is now 47 files, still all verifying clean.

**Dead code removed, not just left in place.** `package.json`'s `build`
script (`esbuild assets/canvas/**/*.js …`) targets a glob that matches
zero files — every scene here is a self-contained inline `<script>`,
nothing gets bundled — and running it confirmed the failure mode: exit 0,
an `[empty-glob]` warning, no `dist/` output, a script that looks like it
succeeded while doing nothing. No workflow depends on it and nothing in
`README.md`/`SETUP.md`/`ARCHITECTURE.md` documents it. Removed it along
with the now-orphaned `esbuild` devDependency. The same
grep-every-import-style check that caught this also found `d3` and
`cannon-es` declared as dependencies but referenced nowhere in the
project — no script, no canvas HTML, no CDN import map. Removed both.

`.gitignore` was missing `tests/diffs/` — the visual-regression script's
failure-debugging output, produced only on a failed comparison and
uploaded as a CI artifact by `tests.yml`, never meant to be committed.
`tests/baselines/` correctly stays un-ignored (it's the durable
comparison reference the script checks future runs against, by design —
confirmed from the script's own code comments before treating the
asymmetry as a bug). Added the one missing line.

## Third-party dependencies — what's owned vs. what isn't

GitHub's markdown renderer strips `onerror` and other JS attributes from
embedded HTML, so there's no way to build a real automatic image fallback
inside a README — "if this external image fails, show that one instead"
isn't achievable there no matter how it's wired. Given that constraint,
the honest approach is: eliminate every external dependency that *can*
be self-hosted, and plainly document the ones that structurally can't.

**Eliminated:** the header/footer wave graphics used to come from
`capsule-render.vercel.app` — a third-party rendering service with its own
uptime and its own risk of disappearing. They're now `assets/svg/ui/wave-header.svg`
and `wave-footer.svg`, hand-authored and committed in this repo like everything else.

**Kept, and why:** the profile-view counter (`komarev.com/ghpvc`) requires
a persistent server-side counter — that's not something a static SVG or
client-side script can replicate without standing up real backend
infrastructure, which is out of scope for a profile README. Badge
rendering (`img.shields.io`) is kept for the same reason every GitHub
profile on the platform uses it: there's no realistic self-hosted
equivalent for on-demand dynamic badge images. Both are accepted,
documented dependencies rather than something quietly hoped nobody notices.

## Font strategy

GitHub's SVG renderer strips `@import url(fonts.googleapis.com)` silently — the font simply
doesn't load and the browser falls back to a serif default, breaking the visual design. Every
SVG in `assets/svg/` uses a system font fallback stack instead:

- Display headings: `Orbitron, Impact, 'Arial Narrow', Arial, sans-serif`
- Monospace body: `'Share Tech Mono', 'Courier New', Courier, monospace`

The Orbitron/Share Tech Mono actual fonts load correctly in the GitHub Pages portal and 3D
scenes (served via a real HTTP server where `<link>` tags work), just not in GitHub's
markdown-embedded SVG renderer.

## Final verification round — new findings

This round re-ran every mechanical check from scratch before looking for
anything new: `npm install`, `npx vitest run`, `node tests/visual-regression.js`,
`sha256sum -c`, `node --check` on every standalone and inline script, and a
strict XML parse of every SVG (39, not just the 31 under `assets/svg/` —
`assets/generated/` and `assets/portal/og-card.svg` included this time).
All of it passed exactly as documented above. Three real,
previously-undocumented issues turned up, plus one mistake made and
caught within this same round.

**CI pipeline was completely broken — no committed lockfile, but nine
`npm ci` steps depend on one.** `.gitignore` never excluded
`package-lock.json`, but the file was never actually committed either — a
gap, not a deliberate choice; `SETUP.md` only ever documents `npm install`
for local setup, which doesn't need one. `npm ci`, used in
`tests.yml` (×2), `update-readme.yml` (×4), `render-3d-previews.yml`,
`lighthouse-ci.yml`, and `deploy-pages.yml`, hard-requires an existing
lockfile and refuses to run without one — confirmed empirically in this
environment (`rm package-lock.json && npm ci` fails immediately with a
usage error, before dependency resolution even starts). That means every
one of those workflows would have failed at the install step on a fresh
clone, every time. Fixed by generating a real `package-lock.json` from
this project's actual `package.json` and committing it — re-verified with
`rm -rf node_modules && npm ci`, which now succeeds (248 packages), and a
full `npx vitest run` afterward (29/29) to confirm the resulting
`node_modules` is equivalent to the one every prior round used.

**LOC badge drift traced to its actual cause, and `count-loc.js` hardened
against it.** Running `count-loc.js` fresh in this session showed 16,499
lines against the README's committed "11.8k" badge — a much bigger gap
than normal day-to-day drift would produce. Investigated rather than
assumed: the difference was almost entirely `package-lock.json` itself
(4,152 of the ~4,700-line gap), which `npm install` had just generated in
this working copy and which `count-loc.js` was never taught to exclude —
the same class of problem the script already solves for
`assets/generated/*.svg`, just not extended to lockfiles, because no
lockfile had ever existed in the repo before this round. Left as-is,
committing `package-lock.json` for the fix above would have permanently
polluted every future "hand-written LOC" count with generated content.
Added an `EXCLUDE_FILES` set (`package-lock.json`, plus `yarn.lock` and
`pnpm-lock.yaml` defensively, though neither is in use) alongside the
existing `EXCLUDE_PATH_SUBSTR` mechanism. Re-run after the fix: 12,362
lines — consistent with ordinary drift since the badge was last
regenerated (this file alone has grown by several hundred lines across
verification rounds), not a new discrepancy.

**Static SVG assets use SMIL for motion, which `prefers-reduced-motion`
CSS cannot reach — a gap the nine-3D-scene reduced-motion pass never
covered, because that pass was scoped to `requestAnimationFrame`-driven
Canvas/WebGL scenes, and these files use neither.** Every reduced-motion
fix documented elsewhere in this file works by forcing CSS
`animation-duration`/`transition-duration` to near-zero, or by freezing a
JS-side clock. Neither mechanism touches SMIL (`<animate>`,
`<animateMotion>`, `<animateTransform>`) — a separate, older animation
system with its own `dur`/`begin`/`repeatCount` attributes that CSS
animation properties don't address. This is standard web-platform
behavior, not something that needed a browser to confirm structurally. A
repo-wide sweep for SMIL elements found 17 files using them; all 17 rely
solely on the CSS-only reduced-motion pattern, so all 17 share this gap
in principle. Of those:

- `assets/canvas/system-map/index.html` — four traveling "data flow" dots
  along static, always-readable node/link paths. Purely decorative, safe
  to hide outright. **Fixed this round**: added a `.pulse-dot-anim` class
  to the four dots and a `display:none` rule under
  `prefers-reduced-motion: reduce`, and separately removed a
  `.pulse-dot` / `@keyframes pulse-travel` CSS rule that turned out to be
  dead code from an earlier, CSS-only version of the same effect — no
  element in the file ever carried that class; the real implementation
  had already moved to SMIL. Re-verified with a strict XML parse of the
  embedded `<svg>` after the edit.
- `assets/svg/diagrams/layer-stack.svg` (13 SMIL elements),
  `assets/svg/ui/neon-divider.svg` (6), `assets/svg/diagrams/system-map.svg`
  (4, the static twin of the file above), `assets/svg/ui/hud-card.svg` (1),
  and `assets/svg/sections/section-01.svg` through `section-09.svg` (1
  each) — same category as system-map: traveling pulses or a pulsing
  accent bar, layered on content that reads fine without the motion. Same
  fix pattern would apply cleanly. **Fixed in the SMIL reduced-motion
  remediation section further below**, along with a real mistake caught
  mid-fix on `neon-divider.svg` that's worth reading if you're touching
  that file again.
- `assets/svg/science/atom.svg` (11 SMIL elements, 6 of them
  `animateMotion` orbits) and `assets/svg/science/dna-helix.svg` (2) were
  grouped together here as the same kind of case — the animated circles
  *are* the electrons / the traveling highlight, not chrome on top of
  separately-readable content, so hiding them the same way as everything
  else would leave an orbit-less nucleus or a bare helix. **That turned
  out to only be true for `atom.svg`** — see the SMIL reduced-motion
  remediation section below, where closer reading of `dna-helix.svg`
  found its two dots really are decoration on an already-complete
  structure, correcting this grouping before doing anything with it.
  Both are fixed now, `atom.svg` with the static-position fallback
  flagged as necessary here.
- `assets/svg/hero/glitch-name.svg` (4 SMIL elements) is the most
  structurally involved: two are the RGB-split "glitch flash" copies of
  the name (safe to hide — the main name text is a separate, always-
  visible element), but the other two drive the `feTurbulence`/
  `feDisplacementMap` distortion filter applied to that main, always-
  visible name text itself (`filter="url(#glitch-distort) url(#glow-base)"`
  on the primary `NOOR ALHUSSAIN` text element). Hiding the text isn't an
  option there; the fix is a CSS class that overrides `filter` to just
  `url(#glow-base)` under reduced motion, dropping the distortion chain
  without touching the text's visibility. **Fixed as described, below.**

**A mistake made and caught within this same round, in the interest of
the same honesty this file asks of everything else:** the first version
of the `system-map` fix above wrote a CSS comment that literally
contained the text `<animateMotion>`. Harmless to a browser's CSS parser,
but a strict XML parser reading the embedded `<svg>` has no concept of

the file failed the same strict-XML-parse step every modified SVG goes

inspection; rewritten without literal angle brackets around the element
name and re-verified well-formed.

**A real bug in the `Uniforms` struct's WGSL/Rust layout, missed by the
earlier comparison referenced above because that comparison summed raw
field sizes instead of applying WGSL's actual alignment rules.** WGSL's
uniform-address-space layout gives `vec3<f32>` a 16-byte alignment —
same as `vec4<f32>` — despite its own size being 12 bytes; this is a
well-documented, spec-mandated rule (part of the WGSL spec itself, not
implementation-specific, so it doesn't need a live GPU to confirm
structurally, the same reasoning already used elsewhere in this file for
web-platform facts that don't need a browser). Working through
`shader.wgsl`'s `struct Uniforms { mvp: mat4x4<f32>, time: f32, _pad:
vec3<f32> }` field by field: `mvp` occupies bytes `[0,64)`, `time`
`[64,68)`, then `_pad` needs 16-byte alignment, so the compiler inserts
an implicit 12-byte gap before it — `_pad` actually starts at byte `80`,
not `68` — and the struct's overall alignment (16, the max of any
member) rounds the final size up to `96` bytes, not the `80` a naive sum
gives. On the Rust side, `_pad: [f32; 3]` is a plain array with no such
alignment bump (`repr(C)` gives it the alignment of `f32`, which is 4),
so `bytemuck::cast_slice(&[uniforms])` actually produced an 80-byte
buffer — 16 bytes short. `min_binding_size` on the bind group layout
entry is `None`, which makes wgpu validate the bound buffer's real size
against the shader-computed minimum at `create_bind_group` time, so an
80-byte buffer against a 96-byte requirement should fail that validation
outright, refusing to render — every scene depends on that same
`bind_group`, so this wasn't a cosmetic issue, it was would-be total
scene failure. This is exactly the kind of thing the "no Rust toolchain,
no real browser" constraint in this environment makes structurally
impossible to catch by actually running it — it needed working through
the WGSL and repr(C) layout rules by hand instead, the same "logic
reviewed, not compiled" standard already applied to the `rust-engine`
`matchMedia` check elsewhere in this file. **Fixed**: widened `_pad` to
`[f32; 7]` (28 bytes), bringing the Rust total to 96 — matching WGSL's
required minimum exactly, confirmed independently in Python rather than
by hand a second time. `_pad` is never read on the shader side, so the
fix only needs to reach the same total size, not mirror WGSL's exact
internal gap position. Updated both places `Uniforms` gets constructed
(initial setup and the per-frame update), and corrected the earlier,
inaccurate claim in the Rust section above accordingly.

competing with a SMIL animation on the same property — nothing animates

## WCAG 2.2 audit — all nine interactive scenes, plus the four tools

WCAG 2.2 became the formal standard (ISO/IEC 40500:2025) in late 2025.
WCAG 3.0 isn't a realistic compliance target until 2028 or later, so 2.2 AA
is the concrete, current target — not "accessibility" as a vague aspiration.

This audit was done in two passes. The first covered the four functional
tools (`compiler-playground`, `memory-visualizer`, `timing-demo`,
`sat-solver`) for Target Size Minimum and Focus Appearance, detailed below.
The second pass covered the nine original 3D/canvas scenes (`atom-3d`,
`dna-3d`, `particle-field`, `skill-universe`, `hologram-cube`, `neural-net`,
`wormhole`, `cpu-die`, `rust-engine`), none of which had `prefers-reduced-motion`
support, a visible `:focus-visible` indicator on the "back" link, or a
`role="img"` + `aria-label` on the canvas — a canvas element has no
accessible-name semantics of its own, so without an explicit label a screen
reader announces nothing about what the scene shows. Every scene now carries
the same three fixes, plus real fallback UI for the two scenes
(`skill-universe`, `neural-net`) that had none: previously, if WebGL/WebGL2
context creation failed, `skill-universe` would throw an unhandled
`TypeError` from inside the OGL library with a blank black screen and no
explanation, and `neural-net` would do the same from its raw `gl.*` calls.
Both now check for a null/failed context up front and show the same
fallback message used by `atom-3d`/`dna-3d`. `hologram-cube` and `cpu-die`
were also missing the top-right engine `#badge` present on every other
scene; both now have one.

Two of 2.2's new success criteria, plus one long-standing 2.0-era AA
criterion (text contrast, checked separately below since it isn't new to
2.2), were checked against actual computed CSS values (font-size + padding
for the first two, relative luminance for the third — not eyeballed)
across `compiler-playground`, `memory-visualizer`, `timing-demo`, and
`sat-solver`:

**Target Size Minimum (interactive elements need ≥24×24 CSS px):**

| Element | Before | After |
|---|---|---|
| `.ex-btn` (compiler-playground example buttons) | ~22px | ~28px, `min-height:24px` added |
| `.lit` (sat-solver) | ~19px | removed — dead CSS, never instantiated in the DOM, not a real user-facing target |
| Every other button (`.run-btn` variants) | 34–40px | no change needed |

**Focus Appearance (focus indicators need real visibility and contrast):**
Three of the four tools had `outline:none` on text inputs/textarea/select
with only a subtle border-color shift standing in for a focus indicator —
too weak against a near-black background for reliable keyboard navigation.
Fixed with a single shared rule in every tool:

```css
:focus-visible{outline:2px solid #00ffff;outline-offset:2px;}
```

`:focus-visible` (rather than plain `:focus`) shows this only for keyboard/
programmatic focus, not mouse clicks — a pseudo-class selector's
specificity outranks a plain element selector's, so this correctly
overrides the older `outline:none` rules without needing to touch them.
Cyan-on-near-black clears WCAG's contrast requirement by a wide margin,
and matches the site's existing glow language instead of looking bolted on.

**Text Contrast (WCAG 1.4.3, AA — normal text needs ≥4.5:1 against its background):**

Every `color:` declaration in the four tools' CSS was extracted and checked
programmatically — relative luminance and contrast ratio computed per the
WCAG formula, not eyeballed — against the page background (`#0a0812`), with
button text checked against its actual button background instead where that
applied (`.run-btn` text is dark-on-cyan/violet, not dark-on-page, and both
clear contrast comfortably: 15.85:1 and 5.96:1).

This turned up a real, if narrow, gap: fourteen low-alpha text rules across
the four tools — badges, subtitles, labels, addresses, and status text —
sat between 2.13:1 and 4.39:1, all short of the 4.5:1 floor for normal-size
text. The fix was to raise alpha on the affected `rgba(...)` text colors
(mostly to 0.55, a couple to 0.5/0.85 depending on the base hue) until each
one cleared 4.5:1 with real margin, verified the same way, not just nudged
and assumed. One case needed more than an alpha bump: the violet label text
(`#8a2be2` / `rgba(138,43,226,…)`) tops out at 3.34:1 even at full opacity —
too dark a violet to ever reach 4.5:1 against this background regardless of
alpha. Those rules were switched to the lighter violet (`#bb88ff`) already
used elsewhere in the same files for token highlighting, which reaches
7.65:1 at full opacity and comfortably clears the floor at the alpha
already in use. A related instance of the same near-miss (`rgba(0,255,255,0.5)`
at 4.39:1) was found in the shared `#back` link style, which is identical
across all fourteen `assets/canvas/*/index.html` files, not just the four
tools — fixed there too, for the same reason: it's real link text used for
keyboard/screen-reader navigation, not decoration.

The same measurement pass was then extended to the remaining ten
`assets/canvas/*/index.html` files — the nine original 3D scenes plus
`system-map` — since their shared `#label`/`#badge` HUD styles were built
from the same low-alpha cyan pattern already shown to fail in the four
tools. That suspicion held: `#label` (`rgba(0,255,255,0.4)`, 11px, 3.16:1)
and `#badge` (`rgba(0,255,255,0.3)`, 9px, 2.24:1) were failing identically
across all nine 3D scenes, and `system-map` (not one of the nine 3D scenes,
but in the same directory and sharing the same visual language) had its own
instances of the same `#badge`/`.sub` pattern plus a `.legend` line at
`rgba(232,232,240,0.35)` (2.77:1). All raised to 0.55 alpha, same fix,
same margin, same verification method. `system-map` has no `<script>` tags
at all — it's static HTML/CSS/SVG — so the fix there was CSS-only with no
syntax to re-check.

**Non-text Contrast (WCAG 1.4.11, AA — UI component boundaries need
≥3:1), a separate criterion from the text-contrast pass above.** Every
`.4.3` fix so far was about text you read; this one is about borders you
need to see to know a control exists. Checked the resting-state (not
`:focus`) borders on every genuinely interactive element across the four
tools plus the shared `#back` link across all fourteen scenes — text
inputs, a textarea, buttons, a `<select>`, and the link. All of them used
`rgba(0,255,255,0.1)`–`rgba(0,255,255,0.2)` at rest, giving 1.49:1–1.59:1:
visible once focused (the focus-state alpha was already fixed and
compliant), invisible at rest. Also included two elements that aren't
interactive controls but are graphical objects a reader depends on to
parse program state — `compiler-playground`'s `.tok-id`/`.stack-cell` cell
borders and `sat-solver`'s `.var-cell` borders — at `rgba(0,255,255,0.3)`
(2.24:1). All raised to 0.4 alpha (3.16:1, real margin). Deliberately
**not** touched: `.panel`/`.stage`/`.status`/`.verdict`/`.builder`/
`#badge` borders — these are decorative framing and non-interactive
status containers, not UI components or content-bearing graphical
objects, so 1.4.11 doesn't apply to them; leaving their low-alpha borders
alone is a judgment call, not an oversight.

**Not applicable:** Dragging Movements (2.5.7) — none of the four tools
use drag interactions.

**Language of Page (WCAG 3.1.1)** — confirmed `<html lang="en">` present
on all fourteen scenes; no gap.

**Keyboard Accessible (WCAG 2.1.1) — investigated, turned out to be a
pass, not a bug.** None of the nine 3D scenes have any keyboard event
handler, which looked like a likely gap given several have mouse-driven
camera rotation. Checked whether that rotation is required to see the
content or just an optional enhancement: every scene with orbit-style
camera controls (`skill-universe`, `hologram-cube`, `cpu-die`, and the
Three.js/OGL-based scenes generally) sets `autoRotate: true`
unconditionally at initialization, so the full visual — the thing a
keyboard-only user actually needs to perceive — plays automatically
without any pointer interaction. Dragging is a manual override on top of
that, not a gate in front of it. `skill-universe`'s aria-label previously
read "…orbiting a shared center, drag to rotate", which read as though
dragging were required; reworded to "auto-rotating…drag to rotate
manually" so the label matches the actual behavior instead of
overstating what interaction the scene needs.

**Use of Color (WCAG 1.4.1)** — checked whether any of the four tools'
state indicators rely on color alone. They don't: `sat-solver`'s
variable cells show literal `T`/`F`/`?` text alongside the green/red/gray
color coding, not just the color; `memory-visualizer`'s overflow states
each write full explanatory text into `#status` ("STACK CANARY
CORRUPTED", "OVERFLOW REACHED RETURN ADDRESS", etc.) rather than
signaling through color and animation alone. No gap found here.

**Status Messages (WCAG 4.1.3) — a real, previously-uncovered gap
affecting all four tools equally.** Every one of the four tools' primary
result region — `compiler-playground`'s `#out-ast`/`#out-vm`,
`memory-visualizer`'s `#status`, `timing-demo`'s `#verdict`,
`sat-solver`'s `#verdict` — updates its content dynamically via
`innerHTML`/`textContent` in response to running the tool, with zero
`aria-live` region anywhere in any of the four files. A screen reader
user compiling a program, moving the buffer-overflow slider, running the
timing benchmark, or solving a formula would get no announcement that
anything happened at all — they'd have to manually re-navigate to the
result area after every interaction to discover it changed. Added
`aria-live="polite"` to all five regions (both compiler-playground
targets, since `CompileError` can surface in either `#out-ast` or
`#out-vm` depending on which stage fails). Deliberately used `polite`,
not `assertive`, everywhere — WAI-ARIA guidance reserves `assertive` for
truly interrupting, time-critical updates, and none of these four tools'
results are that; `polite` waits for a natural pause instead of cutting
off whatever the screen reader was already announcing. Deliberately
**not** added to `sat-solver`'s `.assignment` region (the per-variable
breakdown) — it updates alongside `#verdict` on every solve, and
announcing both at once would mean re-reading every variable's value
aloud on every run; the verdict text already carries the essential
SATISFIABLE/UNSATISFIABLE signal, and the full per-variable detail
remains reachable through ordinary navigation without forcing it to be
read aloud every time.

**Reduced Motion — the CSS fix wasn't the real fix (WCAG 2.3.3 territory, not
just cosmetic transition-duration).** The `prefers-reduced-motion` CSS added
earlier only zeroes `animation-duration`/`transition-duration` — it has no
effect on `requestAnimationFrame` loops or WebGPU/WebGL render loops driven
by elapsed time, which is exactly what actually rotates cameras, orbits
electrons, and drifts particles in all nine 3D scenes. That CSS fix was real
but incomplete; the loops kept running at full motion regardless of the
OS-level setting. Went through each scene's actual animation driver and
gated the *time value itself*, not just CSS:

- `atom-3d` / `dna-3d` (Babylon.js): two separate motion sources per scene,
  not one — the custom `onBeforeRenderObservable` loop (electron orbits,
  nucleus pulse) *and* Babylon's built-in `camera.useAutoRotationBehavior`,
  which is driven internally by the library, not by any variable this
  codebase controls. Freezing `dt` in the custom loop alone would have left
  the camera still auto-orbiting. Both gated behind one
  `matchMedia('(prefers-reduced-motion: reduce)')` check computed once at
  init.
- `particle-field` (WebGPU compute): the shader uses `u.time` directly for
  noise-field drift, rotation angle, and pulsation — not only `u.dt` for
  position integration. An earlier pass at this fix froze only `dt`; re-
  checked the actual WGSL body and found `time` was still advancing on its
  own, which would have left the noise-driven drift and pulse running.
  Both frozen together.
- `skill-universe` (OGL): same two-source pattern as the Babylon scenes —
  OGL's `Orbit` controls take `autoRotate` as a constructor option (not
  toggleable via a variable the render loop touches), separate from the
  node-pulse `dt` in the manual `update()` loop. Both gated.
- `hologram-cube` / `cpu-die` (Three.js `OrbitControls`): `controls.autoRotate`
  at init, plus each scene's own `clock.getElapsedTime()`-driven effect
  (scanline shader time; the explode/assemble layer cycle). `cpu-die` had a
  third wrinkle: an `'end'` event listener that force-reset
  `autoRotate = true` after every drag, which would have silently undone
  the reduced-motion preference the first time someone interacted with the
  scene — gated that listener's registration too, not just its target
  value.
- `neural-net` (raw WebGL2): the obvious per-frame `dt` (node glow decay,
  signal propagation), plus two `setInterval` timers that spawn new signal
  pulses on a fixed schedule, entirely independent of the animation loop —
  freezing `dt` alone would have left new pulses appearing (frozen at
  spawn) every 1.8–3.2 seconds. Suppressed both intervals; one initial wave
  still fires so the diagram isn't blank.

  **A real bug introduced and caught mid-fix, not shipped:** the first
  version of this edit declared
  `const reduceMotion = matchMedia(...)` down at the render-loop section
  but referenced it earlier, at the interval-suppression `if` — a
  temporal-dead-zone `ReferenceError` that `node --check` doesn't catch
  (it's a runtime scoping error, not a syntax error). Caught by actually
  reading the declaration-vs-use line numbers before considering the file
  done, not by a tool. Fixed by moving the single `const` declaration to
  right after the WebGL2 context guard, before any use; verified with
  `node --check` plus HTML re-validation, and by re-grepping to confirm
  the declaration now precedes every reference to it.
- `wormhole` (raw GLSL fragment shader): the entire visual is one
  continuously swirling shader driven by a single `t` uniform — arguably
  the most vestibular-intense of the nine scenes given its explicit
  hypnotic-swirl design. Froze `t`; left the mouse-follow parallax alone
  since it only moves in direct response to real cursor movement, not on
  its own.
- `rust-engine`: structurally different from the other eight — the render
  loop is compiled Rust/WASM, not editable JS, so the fix has to live in
  `lib.rs` itself and can't be verified by running anything here. Added a
  `reduce_motion: bool` field read once via
  `web_sys::window().match_media("(prefers-reduced-motion: reduce)")` at
  `State::new()`, and used it to freeze the `time` value `render()` passes
  into `math::build_mvp()` (the sole driver of the voxel sphere's
  rotation). Added the `MediaQueryList` feature to `Cargo.toml`. Brace/
  paren balance and TOML validity both check out, and the `.ok().flatten()`
  chain matches the standard, widely-used wasm-bindgen idiom for this exact
  check — but repeated attempts to fetch web-sys's generated source for
  `Window::match_media`'s precise return-type signature kept hitting page-
  truncation in this environment before reaching that specific method
  (alphabetically-unsorted, deep in a 3000+ line generated file). Flagging
  this honestly rather than asserting compiler-verified certainty: this
  fix is reviewed by hand against a well-established pattern, in the same
  "logic reviewed, never compiled here" category as the rest of the Rust
  code in this project, not a stronger claim than that.

Also refined `skill-universe`'s aria-label — it read "…drag to rotate" in a
way that implied dragging was required, when every scene with orbit
controls (this one included) auto-rotates unconditionally regardless of
interaction. Reworded to "auto-rotating…drag to rotate manually" so the
label describes what the scene actually does.

## Decoration vs. substance — measured, not assumed

Industry commentary in 2026 has turned against animated-SVG-heavy,
badge-heavy profile READMEs as signal-to-noise has shifted toward things
that are independently verifiable — GitHub's own contribution data,
functional demos, structured data — over pure visual flourish. That's a
real, current, sourced observation, not house style.

Rather than cut decorative elements (`neon-divider`, `matrix-rain`,
`hex-grid`, `circuit-lines`, the wave header/footer) on a vibe, the actual
line-by-line balance was measured: 16 references to purely decorative
elements versus 17 references to functional tools, live data, or
verifiable content, out of 327 total lines in `README.md`. That's already
roughly even, and every addition made in this specific pass — Artifact
Attestations, the WCAG audit, JSON Resume, the dead-link fix — was
substance, not decoration. No destructive edit was made here, because the
data didn't support one; removing working, harmless visual polish to chase
a trend would have been change for its own sake, not an actual improvement.

## Dependency & upgrade notes (researched, not guessed)

A deep pass was done to check whether the 3D library versions pinned
throughout this repo were current, and to upgrade what could be upgraded
*safely*. Some conclusions here are "leave it alone" — that's a real
conclusion, not a skipped task, when the alternative is shipping an
unverifiable change to a live scene with no way to test it before it ships.

**Babylon.js (`atom-3d`, `dna-3d`) — deliberately left as-is.**
These load `https://cdn.babylonjs.com/babylon.js` with no version in the
URL, meaning they always run whatever Babylon considers "latest stable" —
currently 9.14.0. Two things were checked before deciding whether to pin
this to a fixed version:

1. Babylon's own team confirmed on their official forum that
   `cdn.babylonjs.com` does not serve arbitrary versioned URLs — only
   latest-stable and latest-preview. A URL like
   `cdn.babylonjs.com/9.14.0/babylon.js` looks plausible but doesn't
   actually exist; there's an open GitHub issue (BabylonJS/Babylon.js#12335)
   proposing that exact schema, still unresolved.
2. The real alternative — `cdnjs.cloudflare.com`, which Babylon's team
   themselves point people to for pinned versions — currently mirrors
   **8.20.0**, a full major version *behind* what's live now. Pinning to
   it would have been a downgrade, not a hardening.

So both realistic paths (fabricate a URL that 404s, or pin to something
older than what's already running) were worse than leaving it alone.
Babylon's own docs are explicit that `cdn.babylonjs.com` shouldn't be used
in production at all — the correct real fix is self-hosting the package
via npm and a bundler, which is a genuinely separate, larger task (it
changes the build pipeline for these two scenes) rather than something to
improvise around with an unverified URL.

**Three.js (`cpu-die`, `hologram-cube`) — pinned version not touched.**
Currently pinned to r158 via an unpkg importmap. The current release is
r185, and `THREE.WebGPURenderer` has needed zero extra configuration since
r171, with automatic fallback to WebGL2. That's a meaningful capability
gap worth closing eventually — but both scenes depend on addons
(`OrbitControls`, `EffectComposer`, `RenderPass`, `UnrealBloomPass`,
`CSS3DRenderer`) whose import paths or APIs can shift across 27 releases,
and there is no way to load either scene in an actual browser from this
environment to confirm nothing broke. Left pinned at r158, which is
confirmed working against the code as written.

**wgpu (Rust `void-engine`) — pinned version not touched.**
`Cargo.toml` pins `wgpu = "0.19"`. The current release is 29.0.3 (MSRV
1.87) — a 10-major-version jump with real, documented breaking API changes
along the way. This repository has no Rust toolchain and no network access
to `cargo check` against, so there is no way to catch a broken bump before
it ships. `check-rust.yml` exists specifically to catch problems like this
on first real push — but shipping code expected to fail `cargo check` and
relying on CI to catch it isn't the same thing as doing the upgrade properly.

**OGL (`skill-universe`) — pinned version not touched, lowest-risk case.**
Pinned to 1.0.3; current is 1.0.11, a patch-level gap within the same
stable minor line (unlike the pre-1.0 releases, which OGL's own docs
warn are breaking-change-prone). This is genuinely the lowest-risk of the
four version gaps found. It's still not bumped here, for the same reason
as the others: no browser access to confirm nothing shifted, and "lowest
risk" isn't the same as "verified safe."

**What would actually resolve this:** running each scene in a real browser
after each version bump, one library at a time, with the browser console
open — not a batch upgrade. That's a concrete, scoped task for a session
with real browser access, not something to guess at from here.

## Two-layer integrity verification

There are deliberately two different mechanisms, because they prove
different things and neither alone is sufficient:

**Layer 1 — `assets/integrity-manifest.asc` (SHA-256 checksums).**
Generated by `scripts/generate-integrity-manifest.js`. Answers: *"are these
files, byte for byte, what was hashed?"* Anyone can verify it offline with
zero network access and zero trust in GitHub's infrastructure:

```
sha256sum -c assets/integrity-manifest.asc
```

**Layer 2 — GitHub Artifact Attestation (Sigstore/Fulcio/Rekor).**
Added by the `actions/attest-build-provenance@v2` step in `update-readme.yml`.
Answers a question Layer 1 structurally cannot: *"was this specific file
produced by this specific GitHub Actions workflow, in this specific repo,
on this specific commit?"* This is keyless signing — no private key is
generated, stored, or rotated anywhere in this repo. The signing certificate
is issued by Sigstore's Fulcio CA, valid for the few seconds the workflow
step runs, and the fact of signing is permanently recorded in Rekor's
public transparency log. Verification requires network access and the
`gh` CLI:

```
gh attestation verify assets/integrity-manifest.asc \
  --repo Noor-AlHussain/Noor-AlHussain
```

Layer 1 without Layer 2 proves the file wasn't tampered with in transit,
but not who built it. Layer 2 without Layer 1 would require the `gh` CLI
and network access even for a quick offline check. Together they cover
both the "no dependencies" case and the "who actually built this" case.

## Safety notes on the security tools

The **Memory Safety Visualizer** and **Timing Side-Channel Demo** are educational tools whose
content is identical in intent and scope to standard university-level security course material.
No real process memory is accessed. No machine code is generated or executed. No network
connections are made from either tool. The timing demo measures its own JavaScript comparison
functions inside the user's own browser — no server-side state is involved.
